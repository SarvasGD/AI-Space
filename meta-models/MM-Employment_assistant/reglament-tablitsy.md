## 2. Формула ячейки-категории (расчёт %)

Для каждой из 5 категорий (не для «Результат» — там своя формула, см. §4):

```
Задача% = (Σ по всем стандартным подзадачам их % выполнения) / (кол-во запланированных подзадач × 100%) × 100
```

Эквивалентная запись через выполненные/невыполненные: `(к-во выполненных подзадач × их % выполнения) / (к-во запланированных подзадач × 100%)`, где невыполненные подзадачи дают 0% и не выпадают из знаменателя.

Каждая стандартная подзадача может быть выполнена не бинарно (0/100), а частично — например, роадмап набросан, но не утверждён = 50% по этой подзадаче, не 100%.

**Откуда берётся «кол-во запланированных подзадач»:**
1. Если источник (резюме/портфолио/памятка) прямо называет план (например, «3 из 5 фич») — берётся оттуда.
2. Если план не назван, но выводится косвенно из структуры источника — вывести оттуда.
3. Если ни то ни другое — берётся стандартное количество подзадач для этой категории из теории гейм-дизайна, см. §3.

## 4. Формула итогового столбца «Результат»

```
Результат% = round( (Σ процентов 5 категорий) / 5 )
```
где категория-прочерк (любого из двух видов, см. §5) считается как 0, **кроме** случая, когда все 5 категорий — прочерк: тогда результат не считается вовсе (0/0), показывается только текст без числа.

## 5. Прочерки — когда, как и почему

Два разных по смыслу случая, оба визуально выглядят как «–» в ячейке категории, но по-разному участвуют в формуле §4.

### (A) Категория структурно неприменима к роли/жанру проекта
Категория **исключается из знаменателя** — не в числителе, не в делителе формулы §4 вообще не участвует.

**Критерий:** могла бы теоретически хоть одна из 4 стандартных подзадач этой категории (§3) в принципе попасть в скоуп данной роли/жанра? Если однозначно нет — исключение.

**Подтверждённые примеры:**
- Encased → Продакт-менеджмент, Мета-игра (короткий аналитический аудит уже вышедшего PC premium сингл-плеер cRPG — ни продукта, ни меты в задаче нет по определению)
- Iron Frontier → Продакт-менеджмент, UX/UI-Дизайн, Мета-игра (узкий фриланс-скоуп: перки, анимации, баланс — резюме подтверждает отсутствие остального)
- Отзвуки серебряного ветра → Мета-игра (настольная игра — меты в видеоигровом смысле не существует)
- Chaffer → Мета-игра, Игровые системы, Баланс (EdTech бизнес-симулятор, эти направления не требовались по задаче)

### (B) Категория применима, но фактически не выполнялась / проект не дошёл до стадии
Категория **считается в знаменателе как 0%**, полноценно участвует в формуле §4.

**Критерий:** хотя бы одна из стандартных подзадач теоретически входила в скоуп роли/жанра, но по факту ни одна не выполнена (не успели, не поручили, проект закрылся раньше срока).

**Подтверждённые примеры:**
- Enchained → Мета-игра (0%, не исключение — просто не дошёл)
- Space Troopers TD → все незаполненные категории (0%, проект закрылся на стадии концепта — это «не успел», а не «не требовалось»)

### Полное исключение строки (особый случай)
Если у проекта **все 5 категорий** попадают под (A) и/или (B) одновременно (то есть везде 0 либо структурное исключение) — результат не показывается числом вообще, только текст пояснения без %. Это уже реализовано в коде (`computeResult()`).

Примеры: Brain DOP, Plutocracy, Color Arena.io, Mini-game Inlostcity, ZooSWAT — везде «вне направлений» текстом, без процента.

## 9. Правила текста внутри ячейки

- **Тест на каждый пункт перед тем, как его оставить:** (1) несёт новый факт о задаче/навыке/артефакте? (2) плюс или минус для впечатления? (3) не дублирует то, что уже сказано в этой же ячейке (включая компакт)? Не проходит хотя бы один пункт — вырезать целиком, не смягчать.
- **Уникальность глаголов в пределах одной строки** (все 5 категорий + результат) — глагол в начале пункта не повторяется больше нигде в этой же строке. При столкновении — синоним.
- **Порядок пунктов — по логике разработки** (что реально шло раньше по процессу), не по алфавиту и не по порядку текста в резюме. В «Игровые системы» core-геймплей — всегда первым пунктом.
- **Честность про роль.** Если задача делегирована/выполнена не самостоятельно — писать через глагол делегирования («поставил ТЗ», «согласовал»), не выдавать за самостоятельное исполнение.
- **Не путать интервью-контекст с CV-фактом.** Детали, важные только для объяснения на собеседовании (например, «финальный визуал потом переделала команда»), в CV не пишутся — если работа реально его, пишется полноценно.
- **Не изобретать факты.** Если конкретики нет ни в одном источнике — писать обобщённо либо не писать вообще, не заполнять для красоты.

## 10. Артефакты — правила ссылок

- Ссылка появляется только если уже реально существует в content.md (в любой секции) или в портфолио .md. Никаких заглушек вида `(#)` в финальном тексте.
- Максимум одна ссылка на категорию, на строке «Артефакт», не на отдельных пунктах списка (у микро-действий отдельных артефактов физически не существует — попытка приписать ссылку к каждому пункту создаёт нечестный слой).
- Если артефакта нет — строки «Артефакт» нет вообще, без пометок «нет ссылки» и т.п.
- **Будущее развитие (не сейчас):** несколько артефактов на одну категорию (например, отдельно по экономике/боёвке/монетизации внутри «Баланс») — плановое улучшение, не делать сейчас. Сейчас — максимум один на категорию, чтобы быстрее закрыть базовый формат по всем 15 строкам.

## 11. Алгоритм сборки одной строки

1. Собрать все пункты по проекту из 3 резюме + портфолио + памятки, без сортировки по категориям.
2. Реклассифицировать по смыслу (§7), не по заголовку источника.
3. Для каждой из 5 категорий решить применимость: (A) структурное исключение, (B) применимо, но 0, или содержательно заполнена — по критериям §5.
4. Для заполненных категорий — определить кол-во запланированных подзадач (§2, приоритет источников) и посчитать % по формуле §2 (или взять готовый, если пересчёт по формуле не согласован — см. открытый вопрос §3).
5. Найти существующий артефакт (§10) в content.md/портфолио для каждой заполненной категории.
6. Расставить пункты в порядке разработки, core-геймплей первым в «Игровые системы».
7. Прогнать тест §9 по каждому пункту, вырезать не прошедшее.
8. Проверить уникальность глаголов в строке.
9. Посчитать «Результат» по формуле §4, сверить вручную.
10. Показать в чате как реальную читаемую таблицу (HTML-превью с нормальной шириной, не code-block и не узкий markdown-рендер чата). Ждать явного апрува.
11. Только после апрува — вносить в content.md/index.html.

## 17. Отложенные (не отвергнутые) варианты оформления

- Мини-STAR (Ситуация→Задача→Действия→Результат) — избыточен для категорийных ячеек, потенциально годится как альтернативный режим просмотра всей строки/проекта целиком.
- Подкатегории внутри ячейки — избыточно при коротких списках, может иметь смысл при 6+ пунктах в категории.
- Действие→Артефакт построчно — отклонено как нечестное (у большинства микро-действий нет отдельного артефакта).
- Действие как markdown-анкер `[текст](url)` построчно — технически дешёвый вариант (переиспользует уже существующий парсинг ссылок), упирается в ту же проблему нечестности на уровне пункта.
- Нумерованный список вместо буллитов — не отвергнут явно, можно предложить как финальный штрих.
